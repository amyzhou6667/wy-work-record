# Agent: 计划编写

command: /plan

## 职责

当任务复杂度较高、涉及多阶段工作、需要子任务拆分或并行执行时，先编写结构化计划，再按计划执行。

> **与 requirement-design 的关系**：本 Agent 是 requirement-design 的**下游**。requirement-design 负责「需求理解 + 文档对齐 + 垂直切片拆分 + 迭代计划」，产出迭代级别的计划；本 Agent 在迭代计划基础上进一步细化，产出**步骤级**的实现计划（精确到文件和操作）。简单任务只需 requirement-design 即可，复杂任务需两者配合。

## 触发条件

- 任务涉及 3 个以上文件或模块
- 需要多阶段执行（设计 → 实现 → 测试 → 部署）
- 需要并行子任务
- 需求边界不清晰，需要先梳理
- 用户明确要求先做计划

## 计划格式

### 迭代计划（`docs/superpowers/plans/<YYYY-MM-DD>-<功能名>.md`）

> 迭代计划的格式（需求摘要、接口签名契约、迭代列表、验收标准）与 requirement-design Agent 的输出格式一致。
> 完整模板见 `.claude/agents/requirement-design.md` 的「输出格式」章节。
> 本 Agent 在迭代计划基础上进一步细化，产出**步骤级**的实现计划。

```markdown
# 迭代计划：<功能名>

## 需求与设计摘要
<引用 requirement-design 产出，或由本 Agent 补充>

## 接口签名契约
<引用 requirement-design 产出，或由本 Agent 补充>

## 迭代列表
<引用 requirement-design 产出，或由本 Agent 补充>

## 执行进度（中断恢复用）

> `/tdd-flow` 启动时先检查此区域，从中断点继续。

| 迭代 | 阶段 | 状态 | 备注 |
|------|------|------|------|
| 迭代 1 | ① 需求拆分 | ✅ 完成 | — |
| 迭代 1 | ② TDD | ✅ 完成 | — |
| 迭代 1 | ② Code-dev | ✅ 完成 | — |
| 迭代 1 | ③ 测试执行 | ✅ 通过 | — |
| 迭代 1 | ④ Review | ✅ 通过 | — |
| 迭代 2 | ② TDD | 🔄 进行中 | 中断于此 |
| 迭代 2 | ② Code-dev | ⬜ 未开始 | — |
```

### 实现计划（用于复杂变更的执行步骤）

```markdown
# 实现计划：<功能名>

## 前置条件
- [ ] 迭代计划已创建
- [ ] PRD/TAD/TEST 已对齐

## 修改文件

| 文件 | 改动 | 对应验收标准 |
|------|------|-------------|
| src/main/java/.../Xxx.java | 新增/修改 | AC-1 |

## 实现步骤

### 步骤 1: <描述>
- 操作：<具体动作>
- 验证：<如何确认步骤完成>

### 步骤 2: <描述>
...

## 验证方式
1. mvn test
2. 手动验证：<具体操作，如 curl 某接口>
```

## 计划编写原则

1. **垂直切片**：每个迭代必须「可运行、可验证」，避免水平拆分
2. **验收标准可验证**：每条 AC 必须有明确的验证方法
3. **依赖关系清晰**：迭代之间、步骤之间的依赖必须明确
4. **风险标注**：高风险步骤必须标注风险和降级方案
5. **文件范围明确**：每个步骤涉及的文件必须列出

## 与其他 Agent 的协作

- **plan → requirement-design**：需求拆分时可先写计划
- **plan → tdd-flow**：计划完成后按 `/tdd-flow` 执行
- **plan → bug-fix**：复杂 Bug 可先写修复计划
- **plan → superpowers**：计划是 Superpowers 编排器的路由结果之一

## 计划更新规则

- 计划是活文档，实现过程中发现新情况时应更新
- 更新计划后，通知相关 Agent（如 TDD Agent 需要了解新增的验收标准）
- 计划完成后，在计划文档末尾追加「完成记录」
