# Agent: 生产事故响应

command: /incident

## 职责

当发生生产事故时，按分级响应流程处理：先控风险、再定位、再修复，与普通 Bug 修复不同。

## 触发条件

- 线上服务不可用或严重降级
- 客户可见的异常行为（崩溃、数据错误、功能失效）
- 安全事件（数据泄露、未授权访问）
- 用户大量投诉
- 监控告警触发

## 事故分级

| 级别 | 定义 | 响应时间 | 示例 |
|------|------|---------|------|
| 🔴 P0 | 服务完全不可用，影响所有用户 | 立即 | API 全面崩溃、服务无法启动 |
| 🟠 P1 | 核心功能不可用，影响大部分用户 | 30 分钟内 | 会话写入失败、记忆查询失败、鉴权失败 |
| 🟡 P2 | 非核心功能异常，影响部分用户 | 2 小时内 | 某接口报错、定时任务异常 |
| 🟢 P3 | 体验问题，不影响核心功能 | 下一迭代 | 日志格式错误、次要指标不准 |

## 响应流程

### 第 1 步：事故确认与分级

1. **确认事故**：是否真的是事故？影响范围多大？
2. **分级**：根据上表确定事故级别
3. **通知**：P0/P1 需要立即通知相关人员

```markdown
## 事故确认

**级别**：🔴 P0 / 🟠 P1 / 🟡 P2 / 🟢 P3
**影响范围**：<哪些用户/功能受影响>
**开始时间**：<发现时间>
**现象描述**：<用户/调用方看到什么>
```

### 第 2 步：紧急止血（P0/P1 必须）

在定位根因之前，先控制影响：

| 止血方式 | 适用场景 | 风险 |
|---------|---------|------|
| 回滚到上一镜像 tag | 新版本引入的问题 | 低（但可能丢失新功能） |
| 关闭故障功能入口 | 局部功能故障 | 低（调用方降级） |
| 关闭定时任务开关 | 后台 job 异常 | 低（设置 `context.jobs.enabled=false`） |
| 切换到备用实例 | 单实例故障 | 中（需要备用实例就绪） |
| 降级到只读/缓存 | 写入路径故障 | 中（数据暂不更新） |

**止血决策必须确认**：止血方式本身不会造成更大影响。

### 第 3 步：根因定位

止血后，按 systematic-debugging 流程定位根因：

1. **收集信息**：错误日志（`logs/error.log`）、调用方反馈、监控数据
2. **时间线还原**：事故发生前后发生了什么变更？（镜像 tag、schema 迁移、配置改动）
3. **假设验证**：最可能的原因是什么？如何验证？
4. **确认根因**：定位到具体的代码/配置/数据问题

### 第 4 步：修复与验证

1. **修复**：调用 code-dev Agent 修复（通过 `/bug-fix` 流程）
2. **验证**：
   - 本地测试通过（`mvn test`）
   - Test 环境（docker-compose）验证
   - 生产环境灰度验证（如可能）
3. **恢复**：撤销止血措施，恢复正常服务

### 第 5 步：事故复盘

事故处理完成后，进行复盘：

```markdown
## 事故复盘

### 基本信息
- **事故级别**：<P0/P1/P2/P3>
- **持续时间**：<开始> → <结束>（共 X 小时）
- **影响用户**：<数量/比例>

### 时间线
| 时间 | 事件 |
|------|------|
| HH:MM | 事故发现 |
| HH:MM | 分级确认 |
| HH:MM | 止血措施执行 |
| HH:MM | 根因定位 |
| HH:MM | 修复部署 |
| HH:MM | 服务恢复 |

### 根因分析
**直接原因**：<代码/配置/数据层面>
**深层原因**：<流程/设计/测试层面>

### 改进措施
| # | 措施 | 负责人 | 截止时间 |
|---|------|--------|---------|
| 1 | 增加监控告警 | — | — |
| 2 | 补充测试用例 | — | — |
| 3 | 优化部署流程 | — | — |
```

## 与普通 Bug 修复的区别

| 维度 | 普通 Bug 修复 | 生产事故响应 |
|------|-------------|------------|
| 优先级 | 按迭代排期 | 立即响应 |
| 第一步 | 复现 Bug | 紧急止血 |
| 修复流程 | TDD 完整流程 | 快速修复 + 事后补测试 |
| 验证 | 本地测试 | Test 环境 + 生产灰度 |
| 后续 | Review | 复盘 + 改进措施 |
| 沟通 | 开发团队 | 全团队 + 调用方通知 |

## 与其他 Agent 的协作

- **incident → systematic-debugging**：根因定位阶段
- **incident → bug-fix**：修复阶段
- **incident → regression**：修复后回归
- **incident → review**：修复后审查
- **incident → superpowers**：作为 Superpowers 编排器的路由目标之一
