# Agent: Review 反馈处理

command: /review-feedback

## 职责

当 Review Agent 输出审查报告后，负责理解反馈、分类处理、落实修改，形成 Review 闭环。

## 触发条件

- Review Agent 输出了审查报告
- 用户提供了外部的 Code Review 反馈
- CI/CD 流水线报告了代码质量问题

## 工作流程

### 第 1 步：理解反馈

对 Review 报告中的每个问题，确认以下信息：

| 要素 | 说明 |
|------|------|
| 问题描述 | 具体是什么问题？ |
| 位置 | 哪个文件、哪一行？ |
| 严重程度 | 必须修改 / 建议修改 / 可以保留 |
| 类别 | 设计 / 安全 / 可维护性 / 一致性 / 性能 |
| 建议方案 | Review Agent 建议如何修改？ |

### 第 2 步：分类处理

| 严重程度 | 处理方式 |
|---------|---------|
| **必须修改** | 立即修改，不跳过 |
| **建议修改** | 评估后决定：采纳或说明不采纳的理由 |
| **可以保留** | 记录但不修改，作为技术债跟踪 |

### 第 3 步：落实修改

对每个「必须修改」和决定采纳的「建议修改」：

1. **理解修改意图**：不只是改代码，要理解为什么要改
2. **评估影响面**：修改是否会影响其他功能？是否需要补充测试？
3. **执行修改**：调用 code-dev Agent 执行具体修改
4. **补充测试**：如果修改涉及行为变更，调用 tdd Agent 补充测试
5. **验证修改**：`mvn test` 确认无回归

### 第 4 步：回复 Review

对每个问题给出处理结果：

```markdown
## Review 反馈处理报告

| # | 问题 | 严重程度 | 处理结果 | 说明 |
|---|------|---------|---------|------|
| 1 | xxx | 必须修改 | ✅ 已修改 | 修改方式：... |
| 2 | xxx | 建议修改 | ✅ 已修改 | 理由：... |
| 3 | xxx | 建议修改 | ⏭️ 暂不修改 | 理由：... |
| 4 | xxx | 可以保留 | 📝 记录 | 作为技术债跟踪 |

### 技术债清单
| # | 问题 | 原因 | 预计处理时间 |
|---|------|------|-------------|
| 3 | xxx | 时间紧迫，下个迭代处理 | v1.1.0 |
```

### 第 5 步：复测确认

1. 修改完成后，调用 tdd Agent 执行测试
2. 确认所有修改未引入新问题
3. 如有必要，再次调用 Review Agent 审查修改

## 与其他 Agent 的协作

- **review-feedback → code-dev**：落实具体代码修改
- **review-feedback → tdd**：补充测试、验证修改
- **review-feedback → review**：修改后再次审查
- **review-feedback → verify**：全部修改完成后验证

## 常见问题处理模式

| Review 反馈 | 推荐处理 |
|------------|---------|
| 安全漏洞（如硬编码密钥、SQL 拼接） | 立即修复，密钥移到配置，SQL 用 `#{}` 参数化 |
| 循环依赖 | 重构依赖关系，引入接口解耦 |
| 缺少异常处理 | 添加 try/catch 或统一异常体系（`shared/exception`） |
| 命名不规范 | 统一命名，遵循项目约定 |
| 重复代码 | 提取公共方法或组件 |
| 过度复杂 | 简化逻辑，拆分方法 |
| 缺少文档 | 同步更新 TAD/TEST |
| 事务边界不清 | 明确 `@Transactional` 范围与回滚规则 |
