# 风险门工作流（Claude Code 适配版）

在执行任何可能产生不可逆后果的操作前，必须通过风险门检查。

## 风险等级分类

### 🔴 高风险（必须确认后才能执行）

| 操作类型 | 示例 | 必须确认的内容 |
|---------|------|--------------|
| 生产写入 | 部署镜像、schema 迁移、真实数据修改 | 环境、安全边界、回滚路径、验证路径 |
| 外部 API 调用 | 真实模型/网关调用、用户身份服务 | 费用预估、隐私影响、凭证安全 |
| 高风险 Git | force push、reset --hard、覆盖远端、删除分支 | 破坏性范围、是否影响他人工作 |
| 数据泄露风险 | 暴露密钥、用户数据、会话内容 | 数据敏感性、是否需要脱敏 |
| 并行写入冲突 | 多 Agent 同时修改同一文件 | 写入范围隔离、合并策略 |

### 🟡 中风险（建议确认，可降级处理）

| 操作类型 | 示例 | 降级方案 |
|---------|------|---------|
| 分支操作 | 创建/切换/合并分支 | 先 stash，确认工作树干净 |
| 依赖变更 | `pom.xml` 修改 | 先锁定版本，测试后再升级 |
| 大范围重构 | 跨模块修改 | 先在 worktree 中验证 |
| API 接口变更 | 修改请求/响应结构 | 先确认向后兼容性 |
| SQL schema 变更 | 加列/改列/迁移 | 先确认向后兼容 + 回滚 SQL |

### 🟢 低风险（可直接执行）

| 操作类型 | 示例 |
|---------|------|
| 只读操作 | 读取文件、检查结构、查看 Git 状态 |
| 本地测试 | `mvn test`、`mvn compile` |
| 本地计划 | 编写计划、设计文档 |
| 安全顺序执行 | 单文件修改、配置调整 |

## 风险门检查流程

```
操作请求
    │
    ▼
识别风险等级
    │
    ├── 🔴 高风险 → 向用户确认 → 用户同意 → 执行
    │                      → 用户拒绝 → 降级或放弃
    │
    ├── 🟡 中风险 → 建议确认 → 用户同意 → 执行
    │                      → 用户跳过 → 降级方案执行
    │
    └── 🟢 低风险 → 直接执行
```

## 降级策略

当高风险操作被拒绝或无法确认时，采用以下降级方案：

| 原操作 | 降级方案 |
|--------|---------|
| 生产部署 | 先在 test 环境（docker-compose）验证 |
| force push | 改为新建分支 + MR 合并 |
| 直接修改主分支 | 在 worktree 中修改，通过 MR 合并 |
| 并行写入同一文件 | 改为顺序执行，指定单一 owner |
| 真实 API/模型调用 | 使用 Mock 数据验证逻辑 |
| schema 迁移 | 先在 H2/Testcontainers 验证 + 准备回滚 SQL |

## 与 TDD 流程的集成

风险门是 TDD 流程的前置检查，不是替代：

```
用户请求 → 环境预检 → 风险门 → 路由 → TDD 流程
                                    ↓
                              快速通道（低风险）→ 直接执行
```

- `/tdd-flow` 和 `/bug-fix` 在执行前自动过风险门
- 快速通道（≤5 行改动、纯配置/文案）可跳过风险门
- 任何涉及生产环境的操作必须过风险门，无论改动大小
