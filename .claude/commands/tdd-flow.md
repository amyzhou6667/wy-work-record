## 执行原则

**全程自动串联，不等待用户确认。** 每步完成后立即进入下一步，最后向用户汇报一次整体结果。中间过程用简短标题行标注进度（如「→ 快速通道 · 阶段②」），不输出冗长说明。

**中断恢复**：启动时先检查迭代计划的「执行进度」区域。如果有未完成的迭代，从中断点继续，而非从头开始。

## 通道选择（开始前先判断，标注在第一行）

| 通道 | 满足条件（任一即可） | 跳过 | 预期耗时 |
|------|-------------------|------|---------|
| **🚀 快速通道** | 纯配置/文案/常量变更；改动预估 ≤ 5 行；Bug 根因与修改位置已明确 | 跳过阶段① | ~5 min |
| **⚡ 标准通道** | Bug Fix（改动 <30 行，不涉及架构）；小功能调整（改动范围 1~2 个文件） | 跳过阶段① | ~10 min |
| **🔄 完整通道** | 新功能；架构变更；涉及多模块；需求边界不清晰；用户明确要求 | 走全部阶段 | ~30 min |

**快速/标准通道**直接从阶段②开始。code-dev Agent 在阶段②前自行探索相关代码，无需 requirement-design 输出的迭代计划——验收标准由需求描述直接转化。

**快速/标准通道的精简契约**：跳过阶段①意味着没有 requirement-design 产出的接口签名契约。此时 code-dev Agent 在阶段②开始前，须先产出一份**精简契约**（仅包含：方法签名 + 参数类型 + 返回类型），写入迭代计划或直接在对话中输出，作为 TDD Agent 和 Code-dev Agent 的共同输入。精简契约不需要 requirement-design 的完整格式，但必须覆盖本次变更涉及的 public API。

**通道回退**：如果执行中发现实际改动超出当前通道的预估范围（如快速通道实际改动 >5 行、标准通道涉及架构变更），**自动升级到更高通道**并补做被跳过的阶段。

## 编排流程

### 阶段 ①：需求拆分（仅完整通道）

1. 调用需求拆分子 Agent，传入需求描述和相关 PRD/TAD/TEST 路径
2. 收集：设计摘要 + **接口签名契约** + 迭代计划（写入 `docs/superpowers/plans/<YYYY-MM-DD>-<功能名>.md`）
3. **完成后立即进入阶段②**

### 阶段 ②：实现（接口先行，tdd + code-dev Agent）

> **接口先行模式**：两者均基于接口签名契约独立工作。
> 1. **TDD Agent**：基于接口签名契约 + 验收标准设计/编写测试用例
>    - 如果实现尚未完成，测试编译失败是预期行为，标注为「待实现」
>    - **不传递 src/main/java/ 实现文件路径作为输入**
> 2. **Code-dev Agent**：基于接口签名契约 + 验收标准实现代码
>    - **绝不传递测试文件路径或内容**
>
> **默认执行顺序：TDD 先行 → Code-dev 后行（串行）**。这是确保测试质量的最可靠路径。
> 如需并行，必须满足以下条件：
> - 接口签名契约足够精确（无歧义的方法签名、参数类型、返回类型、异常声明）
> - 变更范围明确，不涉及跨模块依赖
> - 使用 Workflow 工具的 `parallel()` 或 `pipeline()` 模式

两者均完成后立即进入阶段③。

### 阶段 ③：TDD 执行测试

1. 执行 `mvn test`（或 `mvn test -Dtest=XxxTest`），汇总结果
2. 若失败：code-dev 修复 → TDD 复测 → 循环直到全部通过
3. **通过后立即进入阶段④**

### 阶段 ④：代码审查 + 反馈处理

1. Review Agent 审查 `git diff` + 验收标准，产出审查报告
2. Review-feedback Agent 分类处理审查报告：
   - **必须修改**：立即修改，不跳过
   - **建议修改**：评估后决定采纳或说明不采纳理由
   - **可以保留**：记录为技术债
3. 对需要修改的项：code-dev 落实修改 → TDD 复测 → 重新 review
4. **全部通过后进入下一迭代（回阶段②），或结束**

### 完成

所有迭代 review 通过后，**文档同步与代码提交合并为同一步骤**：

1. 调用 verify Agent 执行完成前验证（代码/文档/Git 三维检查）
2. 执行文档同步（见 CLAUDE.md 检查表）
3. `git add` 代码文件 + 文档文件（一起）
4. `git commit`（代码和文档在同一个 commit 中）
5. 向用户输出汇报：通道选择理由 + 各阶段结论 + review 问题清单

**禁止**：先 commit 代码，再单独 commit 文档。文档不在同一 commit = 未完成。

## 上下文隔离

- code-dev Agent：**绝不传递**测试实现文件路径或内容，只传递需求描述/PRD/TAD/迭代计划（含接口契约）/TC 文字
- tdd Agent：专注测试，基于接口签名契约编写测试，可读 src/main/java/ 实现（只读），可写 src/test/
- review Agent：全部只读，不修改任何文件
