### 考点 1：架构与选型 —— 双存储一致性与选型 Trade-off

#### 1. 问答实录与追问链路
- **面试官原题**：为什么将 MySQL 定义为权威事实源、Qdrant 定位为可重建向量索引？两边数据产生不一致时，架构上如何保障业务正确性与最终一致性？
- **候选人回答**：
  > 向量库负责找最接近的，MySQL 负责找最正确的。用户说“我喜欢喝咖啡”，先写 MySQL 再生成索引存入向量库。查询时先查向量库拿索引，再回 MySQL 查。不会出现不一致，因为以 MySQL 数据为准。向量库没找到会降级到 MySQL 检索。
- **面试官追问**：分布式双写下，MySQL 成功但 Qdrant 写入超时/失败怎么办？“喜欢喝咖啡”与“喜欢喝什么”字面无交集，MySQL 无法简单 LIKE 匹配，工程上如何保障最终一致性？
- **候选人回答**：
  > 向量库找不到有 5 次退避重试，做了轮询机制检查 MySQL 数据有无落到向量库，没有就补。只要 MySQL 数据不丢，向量库数据可以通过轮询机制慢慢补齐。

#### 2. 得分亮点与失分剖析
- ✅ **得分亮点**：准确提炼出“向量库做语义模糊召回，关系库做事实确权与字段完整性校验”的架构分工；追问下给出了“指数退避重试 + 状态表轮询对账补偿”的最终一致性经典范式。
- ⚠️ **失分/短板**：初次回答时存在“不会出现不一致”的经验主义盲区，对分布式网络分区（Network Partition）和双写失败的严重性初期预估不足。

#### 3. 【核心价值】大厂标杆范例参考回答 (Best Practice)
> **大厂架构师标杆回答**：  
> “在 Agent 核心事实与记忆架构中，我们坚持**‘事实强一致，语义检索最终一致，索引全量可重建’**的原则：  
> 1. **选型依据**：MySQL 具备严格的 ACID 事务能力与成熟的多租户行级安全控制，作为唯一的权威事实存储（Source of Truth）；Qdrant 等向量数据库仅作为面向高维语义检索的二级索引（Secondary Index）。单纯依赖向量库无法满足复杂关系查询（如分页、多字段精准过滤、事务一致性），而单一关系库在非结构化自然语言上缺乏泛化语义召回能力。  
> 2. **最终一致性架构（Transactional Outbox / Status 状态机）**：主事务中持久化记忆事实并写入 `embedding_indexes` 状态表（状态为 `pending` 或 `rebuild_required`）。由异步同步服务执行 Embedding 生成与 Qdrant Upsert。成功后原子更新状态为 `active`；若失败则记录错误并触发指数退避重试（带 Jitter）。  
> 3. **极端容灾与降级**：若向量库完全宕机，系统执行**降级策略**——短期会话依赖 MySQL 近期消息窗口与滚动会话摘要（`session_summary`）兜底组装上下文，牺牲跨会话长期记忆相关度，但绝对保障主对话链路 100% 可用；底层向量库故障恢复后，由 `VectorRebuildJob` 基于 MySQL 事实进行批量重灌对账自愈。”

### 考点 2：核心业务实现 —— ContextBundle 组装流水线与 Token 预算控制

#### 1. 问答实录与追问链路
- **面试官原题**：`ContextBuildPipeline` 中多源上下文装配的优先级编排是怎样的？当文本超出大模型 Token 预算上限时，`TokenBudgetTrimStep` 是如何动态裁剪的？
- **候选人回答**：
  > 设置了 Order 排序，重要到不重要依次是本次对话、短期记忆、长期记忆、用户画像。每个内容有专门字数限制，超了就压缩总结或摘要截取。本次对话不能丢，裁剪按不重要到重要从末尾丢弃。
- **面试官追问**：在线链路若实时调用 LLM 压缩总结会造成 P99 延迟飙升数秒，摘要是在线实时压缩还是后台异步预生成？字符数（Characters）与 BPE Token 不对等（中文通常 1 字多个 Token），代码中如何估算？超预算是整块丢弃还是细粒度滑动窗口？
- **候选人回答**：
  > 摘要由后台异步压缩，主链路直接查 MySQL 无需调 LLM。中文 Token 按 4 个字符算是已知技术债。超出预算整块丢弃，从最末尾 Order 最不重要的开始扔。保证当前会话不扔。当前会话超了才调 LLM 摘要总结（唯一影响首字延迟的原因）。

#### 2. 得分亮点与失分剖析
- ✅ **得分亮点**：精准指出“摘要后台异步预计算、主链路直读 MySQL 规避首字延迟”的架构权衡；坦承中文 4 字符/Token 的估算缺陷，展现出清晰的技术自知力。
- ⚠️ **失分/短板**：对当前单条会话过长导致整块丢弃（All-or-Nothing）的边界缺乏消息级别的精细分块截断策略。

#### 3. 【核心价值】大厂标杆范例参考回答 (Best Practice)
> **大厂架构师标杆回答**：  
> “在 `ContextBundle` 装配与预算控制上，核心考量是**‘上下文信息密度最大化’**与**‘主链路 P99 首字延迟（TTFT）零额外损耗’**：  
> 1. **分层优先级与流水线编排**：Pipeline 采用固定权重装配：`CurrentTurnMessage`（核心锚点，优先级最高，绝对保留） > `SystemPrompt & ToolDefinitions` > `RecentMessages`（滑动窗口内关键上下文） > `SessionSummary`（异步预生成的会话压缩摘要） > `LongTermMemories & UserProfile`（Qdrant 向量召回的高相关外部记忆）。  
> 2. **异步预计算解耦**：主请求路径严禁任何同步 LLM 摘要调用。所有会话滚动压缩均由后台 Worker 在轮次间隔异步完成并落库。主流程组装时仅执行内存组装与数学截断。  
> 3. **精确 Tokenizer 与两阶段弹性裁剪**：引入轻量级本地分词组件（如基于 Rust/JNI 的 BPE/Tiktoken 本地库或高精度快速预估系数，中文 1 字符 $\approx$ 1.5~2.0 Tokens）。在 `TokenBudgetTrimStep` 中：第一阶段自底向上剔除边缘可选 Section；第二阶段若单段历史消息超限，执行基于单个 Message 粒度的右滑窗口微裁，保留最近 N 条完整问答对，避免单次丢弃整段引发语义断崖。”

### 考点 3：并发与性能 —— 分布式任务调度与防假死脑裂

#### 1. 问答实录与追问链路
- **面试官原题**：多 Pod 副本并发调度下，`MemoryJobWorker` 如何防止不同节点重复消费同一个 Job？节点崩溃或大模型超时导致任务假死时，如何安全接管？
- **候选人回答**：
  > 使用锁 `SELECT ... FOR UPDATE SKIP LOCKED`。添加了租约，5 分钟过期。只要超过租约时间就释放给其他 Pod 接管。
- **面试官追问**：若 Pod-A 调用大模型耗时 5 分 30 秒，第 5 分 01 秒被 Pod-B 接管，两个 Pod 同时在处理并写回，如何防止重复写入 Qdrant 向量或覆盖最新状态？是否有版本栅栏或幂等机制？
- **候选人回答**：
  > 使用幂等，根据用户 ID、会话 ID 生成的唯一键，有就更新没有就生成。

#### 2. 得分亮点与失分剖析
- ✅ **得分亮点**：答中 MySQL 8.0 `FOR UPDATE SKIP LOCKED` 与基于租约过期的无中心化分布式抢占机制；答出了基于业务维度的复合主键幂等 Upsert。
- ⚠️ **失分/短板**：对分布式租约中的版本号（Version / CAS）与乐观锁栅栏机制未展开阐述。

#### 3. 【核心价值】大厂标杆范例参考回答 (Best Practice)
> **大厂架构师标杆回答**：  
> “针对多节点无中心任务调度与假死脑裂防范，我们的工业级方案包含三道防线：  
> 1. **零争抢无锁抢占**：利用 MySQL 8.0 的 `SELECT id FROM memory_jobs WHERE (status='pending' AND available_at <= NOW()) OR (status='running' AND lease_until < NOW()) ORDER BY available_at LIMIT 1 FOR UPDATE SKIP LOCKED`，各 Worker 瞬间跳过已被锁定的行，实现极高吞吐的无锁并发领任务。  
> 2. **CAS 乐观锁与版本栅栏（Fencing Token）**：在抢占任务置为 `RUNNING` 时，执行 `UPDATE ... SET attempts = attempts + 1, lease_owner = #{workerId}, lease_until = #{newLease} WHERE id = #{jobId} AND status = #{oldStatus}`。在任务完成写回时，更新条件强制携带当前的 `lease_owner` 与 `attempts`。若 Pod-A 慢执行超时，其租约与 attempts 已被 Pod-B 推进，Pod-A 的 CAS 更新行数为 0，系统感知任务被接管，立即主动放弃提交流程。  
> 3. **Qdrant 向量确定性 Point ID 幂等**：向量库中的 Point ID 不采用随机 UUID，而是基于 `SHA256(tenantId + appId + workId + userId + memoryKey)` 生成确定性 UUIDv5。即使两节点并发 Upsert，在 Qdrant 层面也是同键覆盖而非追加冗余，天然具备幂等防重能力。”

### 考点 4：异常与边界容灾 —— 事务边界隔离、死信与突发防浪涌

#### 1. 问答实录与追问链路
- **面试官原题**：`recordTurn` 处理对话落库时事务边界如何划分？外部模型与向量库异常会回滚主事务吗？后台任务达到 5 次重试上限后状态机如何流转？线上死信如何监控与补偿？
- **候选人回答**：
  > 事务只管自己库，不管依赖库。外部系统比如向量库回滚不了，消耗的 Token 费没法回退，不能放进本地事务。状态机是 pending -> running -> dead/completed，失败 5 次进 dead 并留档错误。目前通过日志和计数器监控，无自动重放接口，靠运维 SQL 重置为 pending。
- **面试官追问**：大模型故障恢复后，运维批量将几百条死信重置为 pending，系统如何防止瞬间打崩刚恢复的模型网关？`recordTurn` 接口网络超时时，AgentCore 重试如何避免重复插入消息与审计数据？
- **候选人回答**：
  > 不会打崩，设置是一次 5 条、每次 5 分钟拆分打过去。问题是 500 条需要 8 小时恢复。优化思路是通过 Jitter 和指数退避拆分分批，设置单批上限 100 条。第二个问题会发生，必须做幂等处理，包含 Trace-ID。

#### 2. 得分亮点与失分剖析
- ✅ **得分亮点**：深刻道出“Token 计费与外部向量写操作不可逆，严禁混入本地强事务”的设计铁律；对批量恢复时的长尾延迟与削峰流控（Jitter / Throttling）分析透彻。
- ⚠️ **失分/短板**：对自动化运维死信重放接口（Admin API / Ops Replay）及 TraceId 防重落库的复合唯一索引细节可补充更具体的约束声明。

#### 3. 【核心价值】大厂标杆范例参考回答 (Best Practice)
> **大厂架构师标杆回答**：  
> “高可用架构的精髓在于**‘解耦脆弱依赖、收敛强事务、提供防浪涌补偿’**：  
> 1. **事务边界的强弱隔离**：`recordTurn` 严格收敛在本地 MySQL 强事务中，原子提交 Session、Message、Trace Span 与 Task 事实。外部向量化与抽取动作以轻量级任务或事件形式落库，严禁将 RPC 挂在 `@Transactional` 中，防止连接池泄漏。  
> 2. **自适应指数退避与带抖动削峰（Jitter Throttling）**：针对重试与死信重放，调度器配置 `available_at = NOW() + MIN(maxBackoff, baseInterval * 2^attempts + randomJitter)`。当运维批量激活死信时，系统按租户/应用做滑动窗口令牌桶限流，通过随机 Jitter 将流量在时间轴上均匀打散，杜绝下游模型网关发生雪崩。  
> 3. **端到端幂等控制（Idempotent Turn Boundary）**：`POST /internal/v1/turns` 请求头强制要求携带 `x-trace-id` 或业务 `client_turn_id`。在底层数据库为 `(tenant_id, session_id, turn_id)` 建立唯一索引。当 AgentCore 因超时重试重复提交时，数据库抛出唯一键冲突，服务捕获后转为只读幂等查询，将已落库的记录直接返回，确保 0 重复数据污染。”

### 考点 5：工程与排障 —— 多租户安全与存量向量索引平滑无感重建

#### 1. 问答实录与追问链路
- **面试官原题**：系统如何在 MySQL 与 Qdrant 两个层面强行约束 `tenantId + appId + workId + userId` 四元组防止越权？当发生多租户升级或向量模型更迭时，`VectorRebuildJob` 如何实现不停机、平滑且幂等的全量向量重灌与自愈？
- **候选人回答**：
  > 拦截器解析身份，MySQL 是四层校验租户 ID、用户 ID、工作 ID、应用 ID，是并且的方式，只有四个条件都符合才返回。第二个问题（向量平滑重建机制）不是很清楚。

#### 2. 得分亮点与失分剖析
- ✅ **得分亮点**：准确讲出了拦截器上下文注入与 SQL `AND` 联合四元组硬隔离的纵深防御逻辑。
- ⚠️ **失分/短板**：对 `VectorRebuildJob` 这一关键运维自愈特性的底层状态机机理缺乏了解。

#### 3. 【核心价值】大厂标杆范例参考回答 (Best Practice)
> **大厂架构师标杆回答**：  
> “在多租户安全与底层索引更迭运维中，我们的工程化落地包含两个核心模块：  
> 1. **全链路四元组硬隔离防线**：  
>    - **入口层**：`ApiAuthenticationInterceptor` 强校验 Token 并提取租户上下文注入 `UserContext.Scope`（ThreadLocal/MDC）。  
>    - **数据持久层**：所有 MyBatis 动态 SQL 强制在 WHERE 条件中注入 `tenant_id = #{tenantId} AND app_id = #{appId} AND work_id = #{workId} AND user_id = #{userId}`，避免水平越权。  
>    - **Qdrant 向量检索层**：向量检索过滤条件一律使用 `Filter.must([FieldCondition(key="tenantId", match=tenantId), ...])` 进行前置硬过滤，物理隔绝非当前租户向量。  
> 2. **存量索引平滑热重建状态机 (`VectorRebuildJob`)**：  
>    - **双写与状态标记**：当升级租户隔离策略或模型时，运维在元数据表将存量行标记为 `status = 'rebuild_required'`。  
>    - **微批异步重灌**：`VectorRebuildJob` 定时微批扫描（如 BatchSize=50）`rebuild_required` 数据，逐条调用 `ensureIndexed` 重新生成向量，使用携带新 `tenantId` Payload 的确定性 Point ID 执行 Qdrant Upsert。  
>    - **幂等自愈收敛**：写入成功后，利用 MySQL 的 `ON DUPLICATE KEY UPDATE` 将状态改回 `active`。若过程中 Qdrant 发生故障，单条失败不会推进状态，等待下一轮 Poll 自动重试，全程无需停机，对在线读写完全透明。”

## 🔄 面试复盘操作指引

- 输入 **`--retry`**：针对本次失分考点（如 `VectorRebuildJob` 索引平滑重建、Token 精确分词）重新生成专项深度考题对练。
- 输入 **`--next`**：指定新的本地项目路径或模块，开启全新轮次的大厂实战模拟面试。
