# 缺陷修复工程化技能规范 (Bug-Fix Workflow)

本技能专用于解决代码缺陷、线上异常或功能异常。核心工程铁律为：**先复现找出原因，若有测试文件先修改/补充测试用例，再修改业务代码，杜绝无测试盲改。**

---

## 🎯 核心工程原则

1. **复现第一，严禁盲猜**：在未通过可执行脚本、命令或断言精准复现 Bug 现象前，严禁动手修改业务代码。
2. **测试先行 (Test-First / Red-to-Green)**：
   - 若已有测试文件（如 `*.test.ts`），**必须先在测试文件中新增或修改测试用例**，精确复现故障并使其运行失败（**红灯 Red**）；
   - 若暂无测试文件，需先为该模块建立轻量测试用例（`*.test.ts`），确立回归防御基线。
3. **最小范围精准修复 (Minimal Diff)**：修复代码紧扣根因，不蔓延改动，不引入无关代码或破坏性重构。
4. **零容忍回归门禁 (0 Failures)**：修复后不仅新增测试必须变绿（Green），且所属项目全量测试套件必须 100% 通过（0 失败）。

---

## 🔄 标准执行四阶段流程

### 阶段一：问题解析与最小复现 (Reproduce & Root Cause)
1. **收集故障上下文**：
   - 梳理用户描述、报错日志、异常堆栈（Stack Trace）、终端输出或截图现象；
   - 寻找故障模块源码（如 `projects/<项目名>/src/...`）与已有测试套件（`projects/<项目名>/tests/...`）。
2. **构建最小可复现实验**：
   - 通过原生 Node / TS 命令行或模拟执行脚本运行目标代码；
   - 捕捉底层真实错误（如 `SyntaxError`、`TypeError`、逻辑边界条件错误、MIME/环境缺失等）；
   - 形成清晰的**根因分析结论 (Root Cause Analysis)**。

### 阶段二：测试用例先行 (Red: Modify / Add Test First)
1. **定位并修改测试文件**：
   - 查找对应的测试文件（如 `projects/<项目名>/tests/<模块名>.test.ts`）；
   - 编写一段能够直接触发该 Bug 场景的测试用例（涵盖异常输入、边界数据或模拟环境）；
2. **运行测试验证红灯 (Verify Red)**：
   - 执行测试命令：
     ```bash
     node --test <测试文件路径>.test.ts
     ```
   - **关键门禁**：确认测试准确捕捉到了 Bug 并触发断言失败/错误退出（**Red 状态**）。严禁跳过此步骤直接改代码！

### 阶段三：针对性修复代码 (Green: Fix Implementation)
1. **修改业务源代码**：
   - 定位到故障源文件（遵循全局 TypeScript 规约 `.ts` / `.tsx`）；
   - 实施精准修复，根除导致红灯的缺陷点；
2. **运行测试验证绿灯 (Verify Green)**：
   - 重新执行阶段二的测试命令，确保新用例顺利通过（**Green 状态**）。

### 阶段四：全量回归与成果汇报 (Regression Gate & Delivery)
1. **全量回归测试**：
   - 运行该项目的完整测试套件，确认未产生任何功能退化：
     ```bash
     node --test projects/<项目名>/tests/*.test.ts
     ```
   - 确保 **100% Pass，0 失败**。
2. **向用户结构化汇报**：
   - 🐞 **Bug 根因说明**：发生了什么错误以及产生该错误的底层机理；
   - 🧪 **测试用例先行证据**：先在哪个测试文件新增/修改了用例，红灯报错是什么；
   - 🛠️ **核心修复方案**：修改了哪些源码文件，如何解决该问题；
   - ✅ **验收结果**：全量测试执行与回归通过证明。
